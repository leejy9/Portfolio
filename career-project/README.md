# README.md
> 이 파일은 이 프로젝트(커리어 북두칠성 설계 프로젝트)에 투입되는 모든 에이전트(Claude 포함, 세션·모델 무관)가 **가장 먼저 읽어야 하는 운영 지침서**다.
> claude.md/agent instruction 역할을 한다. 작업을 시작하기 전에 이 파일의 규칙을 따를 것.

## 0. 이 프로젝트는 무엇인가 (30초 요약)
사용자(이재연)는 지금까지 "상황에 적응해서 나쁘지 않은 선택지를 고르는" 수동적 방식으로 커리어를 선택해왔다. 이제 AI 시대에 스스로 욕심낼 만한 커리어 방향(**북두칠성**)을 과학적·구조적으로 정하고, 그 기준으로 후보 회사/직무를 냉정히 비교 평가한 뒤, 빠르게 판단할 수 있는 **행동 기준(decision rule)**을 세우려 한다. 이 저장소는 그 과정의 기록이자 작업공간이다.

## 1. 파일 구조와 각 파일의 역할

| 파일 | 역할 | 읽는 시점 | 쓰는 시점 |
|---|---|---|---|
| **README.md** (이 파일) | 운영 지침서. 전체 규칙과 작업 순서 정의 | 세션 시작 시 항상 최우선 | 규칙 자체가 바뀔 때만 (드묾) |
| **goal.md** | 프로젝트가 무엇을 하려 하는지, 어디까지 왔는지, 뭐가 아직 안 풀렸는지 | README 다음으로 항상 읽을 것 | 새로운 결정이 나거나 단계가 완료될 때마다 갱신 |
| **directory.md** | 용어 사전. 같은 단어를 다른 뜻으로 오해하지 않도록 함 | 대화 중 프로젝트 고유 용어(북두칠성, 희망직무1/2/3 등)가 나오면 참조 | 새 용어가 정의되거나 기존 정의가 바뀔 때 |
| **knowledge.md** | 리서치 원본. 요약·가공 없이 1차 자료 그대로 보존 | 방법론적 근거가 필요할 때 (예: "가중 매트릭스 어떻게 만들지?") | 새로운 Advanced Research를 수행했을 때만, 항상 원본 그대로 추가(기존 내용 삭제·요약 금지) |
| **lessons.md** | 대화를 통해 확정된 사실/판단의 기록 | 이전에 이미 결론 난 것을 재확인할 때 (반복 질문 방지) | 새로운 사실이 확정되거나 기존 정보가 폐기될 때마다 |

## 2. 읽기 순서 (세션 시작 시 반드시 이 순서로)
1. **README.md** (이 파일) — 규칙 파악
2. **goal.md** — 지금 어디까지 왔고 뭐가 남았는지 파악
3. **lessons.md** — 이미 확정된 판단이 있는지 확인 (같은 걸 다시 묻지 않기 위해)
4. **directory.md** — 사용자가 쓰는 용어가 낯설면 여기서 확인
5. **knowledge.md** — 방법론적 근거가 필요한 시점에만 참조 (매번 전체를 읽을 필요는 없음, 필요한 섹션만)

## 3. 쓰기 규칙

### 3.1 knowledge.md — 원본 보존 원칙
- **절대 요약하거나 축약해서 저장하지 않는다.** Advanced Research 결과는 반환된 그대로 전체를 추가한다.
- 기존 내용은 삭제하지 않는다. 새 리서치는 새로운 `#` 섹션으로 append한다.
- 출처(task_id, 날짜)를 반드시 헤더에 남긴다.

### 3.2 goal.md — 최신 상태 유지 원칙
- "아직 해결되지 않은 질문" 목록은 살아있는 체크리스트다. 답이 나오면 체크하고 그 답을 본문에 반영한다.
- 새로운 진행 단계가 생기면 "진행 순서" 섹션에 번호를 이어서 추가한다. 기존 번호는 수정하지 않는다(히스토리 보존).

### 3.3 directory.md — 정의 변경 시 이력 남기기
- 기존 정의를 바꿀 때는 이 파일에서 조용히 고치지 말고, **lessons.md에 "왜 바뀌었는지"를 먼저 기록한 뒤** directory.md를 갱신한다.
- 폐기된 용어/근거는 지우지 말고 "C. 이번 대화에서 폐기/수정된 정보" 같은 별도 섹션으로 이동시켜 보존한다 (예: n8n 경험 폐기 사례 참고).

### 3.4 lessons.md — 사실만, 의견은 금지
- 이 파일에는 **확정된 사실과 그 근거**만 적는다. "~것 같다", "아마도" 같은 추측성 판단은 적지 않는다.
- 형식: `[날짜] 사실/교훈 — 근거 — 영향(향후 판단에 어떻게 반영되어야 하는지)`
- 사용자가 명시적으로 말하거나("~를 삭제했어", "~는 성과가 없었어") 리서치로 확인된 것만 기록. 에이전트의 추측은 기록하지 않는다.

## 4. 판단 원칙 (에이전트가 이 프로젝트에서 지켜야 할 태도)

1. **낙관보다 fit을 우선한다.** 이 프로젝트의 원래 요청 취지는 "내가 하고 싶은 것"을 응원받는 게 아니라, "채용시장/구조적으로 실제로 fit한지"를 냉정하게 검증받는 것이다. 근거 없는 격려나 낙관적 재구성을 하지 않는다.
2. **evidence 강도를 구분해서 말한다.** "말뿐인 지향"과 "실제 경험으로 증명된 강점"을 섞어서 이야기하지 않는다. directory.md의 B섹션(희망직무별 evidence 표)을 참고해 매번 갱신한다.
3. **경험을 강제로 캐묻지 않는다.** 사용자는 "특정 경험을 깊게 파는 것보다 먼저 틀(북두칠성→구조분석→행동기준)을 세우는 것"을 우선시하는 작업 스타일을 보였다(lessons.md 참고). 에이전트가 먼저 나서서 과거 경험 회고를 강요하지 말고, 사용자가 그 단계에 도달했을 때 깊게 들어간다.
4. **폐기된 근거를 재사용하지 않는다.** n8n 사례처럼 사용자가 명시적으로 "성과·배움 없음"이라 판단하고 폐기한 경험은, 이후 어떤 강점 서사에도 다시 등장시키지 않는다.
5. **방법론에 확정성을 과장하지 않는다.** knowledge.md의 Caveats를 존중한다 — 대부분의 커리어 프레임워크는 RCT 근거가 아니라 실무 프레임워크이며, AI 일자리 전망 수치는 모델 추정치다. "이게 답이다"가 아니라 "이 방법론으로 접근하면 이렇다"는 톤을 유지한다.
6. **1단계→2단계→3단계 순서를 건너뛰지 않는다.** 북두칠성(기준)이 없는 상태에서 후보 비교(2단계)를 하거나, 구조 분석 없이 행동 기준(3단계)부터 만들지 않는다. goal.md의 "진행 순서"를 존중한다.

## 5. 이 프로젝트의 알려진 제약사항
- Claude(이 문서를 작성한 에이전트)는 GitHub 쓰기 커넥터가 없어 파일을 직접 리포에 올릴 수 없다. 파일은 로컬 생성 후 사용자가 직접 업로드해야 한다.
- Claude의 메모리 시스템은 세션 간 파일을 자동 공유하지 않는다. 이 저장소(GitHub 등)에 실제로 파일이 존재하고, 매 세션마다 해당 파일을 명시적으로 불러와야만 "연동"이 성립한다.
- 따라서 새 세션/새 에이전트를 이 프로젝트에 투입할 때는, 반드시 이 저장소의 raw 파일 URL 또는 repo 링크를 함께 제공해야 한다.
